# Shared Rules for Both Team Structures

These rules apply to **both Specialists and Generics** experiment runs. They define baseline expectations for git hygiene, branching, testing, and documentation.

---

## Git Hygiene

### Branching
- **Feature branches:** All work is done on branches (`feature/task-0X-*` or variants)
- **No direct commits to main:** All changes go through PRs
- **Branch names:** Use descriptive names (`feature/task-01-filtering`, `fix/priority-sorting`)
- **One task per branch** (or use multiple branches if one task is split across PRs)

### Commits
- **Commit message format:** Use conventional commits:
  ```
  {type}({scope}): {subject}
  
  {body}
  ```
  - Types: `feat`, `fix`, `test`, `docs`, `refactor`, `style`
  - Scope: `task-01`, filename, or feature name
  - Subject: imperative mood, no period
  
- **Example:**
  ```
  feat(task-01): Add status and search filters to GET /tasks
  
  - Validate query parameters (status, search)
  - Implement filter logic in model layer
  - Add integration tests for all filter combinations
  ```

- **Frequency:** Small, focused commits (one logical change per commit)

### Pull Requests
- **Title:** Same as commit message or brief task description
- **Description:** Link to task definition, list acceptance criteria, note any deviations
- **Assignees:** In Specialists mode, assign to Docs/Release. In Generics mode, assign to any available agent
- **Review:** At least one other agent reviews before merge
- **Merge method:** No squash; preserve commit history for audit trail

## Testing Requirements

### Test Coverage
- **Target:** ≥85% code coverage (measured by `npm test`)
- **Minimum:** ≥75% for any commit to main
- **Types of tests:**
  - Unit tests for model layer (data access)
  - Integration tests for API routes
  - Tests for edge cases and error handling

### Test Execution
- **Before merge:** All tests must pass locally
  ```bash
  npm test
  ```
- **After merge:** CI/CD (if available) should also pass tests
- **Test structure:** Use Node's built-in test runner (`node --test`)
- **Test files:** Located in `/app/tests/` (one test file per module)

### Test Naming
- Test file: `{module}.test.js`
- Test cases: Descriptive names with `it()` or `describe()`
- Example:
  ```javascript
  describe('Task filtering', () => {
    it('should filter tasks by status', () => { ... });
    it('should search tasks by title case-insensitively', () => { ... });
  });
  ```

### Coverage Reporting
- Coverage data is generated by `npm test`
- Required for final scoring (record in run logs)
- If coverage drops, QA/Test specialist (or any agent) adds tests to restore it

## Documentation Requirements

### API Documentation
- **Location:** `/app/README.md`
- **Scope:** All HTTP endpoints, query parameters, request/response formats, error codes
- **Format:** Markdown with examples (curl, REST client, or client library calls)
- **Update schedule:** Whenever an endpoint is added or modified

### Example Documentation Template
```markdown
### GET /tasks

Retrieve all tasks with optional filtering.

**Query Parameters:**
- `status` (optional): Filter by status (todo, in-progress, done)
- `search` (optional): Search tasks by title (case-insensitive)
- `sort` (optional): Sort by field (priority, created_at)

**Example:**
```bash
curl http://localhost:3000/tasks?status=todo&search=buy
```

**Response:**
```json
[
  {
    "id": 1,
    "title": "Buy groceries",
    "status": "todo",
    "priority": "high",
    "created_at": "2026-02-13T10:00:00Z",
    "updated_at": "2026-02-13T10:00:00Z"
  }
]
```

**Errors:**
- `400 Bad Request`: Invalid status or sort parameter
- `500 Internal Server Error`: Database error
```

### Code Comments
- **When required:** Complex logic, non-obvious decisions, edge case handling
- **When not required:** Self-documenting code, simple CRUD operations
- **Quality:** Comments should explain "why", not "what"

### Decision Log
- **When required:** All major technical decisions (before merging)
- **What to include:** Decision, options considered, rationale, impact
- **Location:** `/runs/{mode}/decisions.md`
- **Frequency:** ≥10 entries expected per run

## Code Standards

### JavaScript Style
- **Indentation:** 2 spaces
- **Semicolons:** Required
- **Quotes:** Double quotes for strings
- **Naming:** camelCase for variables/functions, PascalCase for classes
- **Example:**
  ```javascript
  const getTasks = (status, search) => {
    const tasks = db.query('SELECT * FROM tasks WHERE status = ?', [status]);
    return tasks.filter(t => t.title.toLowerCase().includes(search.toLowerCase()));
  };
  ```

### No Linting Tool Required
- The app has no built-in linter (no ESLint, no Prettier)
- Code review is informal (agents review each other's PRs)
- Style violations won't block merge, but inconsistency may be flagged in review

## Database & Migrations

### Migration Strategy
- **Location:** `/app/src/db/migrate.js`
- **Execution:** Migrations run automatically on app startup
- **Idempotent:** Migrations should safely run multiple times (use `IF NOT EXISTS`, etc.)
- **Reversible (optional):** No rollback requirement, but prefer reversible migrations

### Example Migration
```javascript
const migrations = [
  {
    version: 1,
    description: 'Create tasks table',
    up: (db) => {
      db.exec(`
        CREATE TABLE IF NOT EXISTS tasks (
          id INTEGER PRIMARY KEY AUTOINCREMENT,
          title TEXT NOT NULL,
          status TEXT DEFAULT 'todo',
          created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
          updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
        );
      `);
    }
  },
  {
    version: 2,
    description: 'Add priority column',
    up: (db) => {
      db.exec(`
        ALTER TABLE tasks ADD COLUMN priority TEXT DEFAULT 'medium';
      `);
    }
  }
];
```

## Acceptance Criteria Verification

### Checklist for Each Task
Before merging, verify:
- [ ] All acceptance criteria from task definition are met
- [ ] All testable requirements pass
- [ ] Edge cases are handled (empty input, invalid values)
- [ ] Error messages are clear
- [ ] Documentation is complete
- [ ] No breaking changes to existing API

### Evidence Required
- Test output (pass/fail, coverage %)
- Code review comments confirming acceptance criteria
- Running the app manually and verifying feature works
- Screenshots or demo (optional but helpful)

## Performance Expectations

### API Response Time
- **Target:** <100ms for most endpoints
- **Complex queries:** <500ms (e.g., bulk operations on 100+ tasks)
- **Measurement:** Log response times in tests or manual testing

### Database Performance
- **Indexes:** Add indexes on frequently queried columns (status, created_at)
- **Query optimization:** Avoid N+1 queries; use joins where needed
- **Transactions:** Use for atomic operations (bulk updates, imports)

## Error Handling

### HTTP Status Codes
| Code | Meaning | Example |
|------|---------|---------|
| 200 | OK | GET /tasks succeeds |
| 201 | Created | POST /tasks creates a task |
| 400 | Bad Request | Invalid query parameter, missing field |
| 404 | Not Found | GET /tasks/999 (doesn't exist) |
| 500 | Internal Error | Database error, unhandled exception |

### Error Response Format
Consistent format for all errors:
```json
{
  "error": "Error message here",
  "code": "INVALID_STATUS",
  "details": { "received": "invalid", "expected": ["todo", "in-progress", "done"] }
}
```
